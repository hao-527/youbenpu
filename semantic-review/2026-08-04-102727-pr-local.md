# Storage compatibility and location-reference re-review

Both previously reported high-severity issues in `storage.ts` are fixed. Future numeric schema versions are preserved and cannot be overwritten by the fallback state, while corrupt or unsupported payloads follow the cleanup path. Case-insensitive location duplicates now resolve to one retained spelling, and inventory items are rewritten to that exact value. **Watch for:** no remaining critical/high issue caused by either fix.

## High-level view

Future-version detection runs before version-specific shape validation and disables `saveState`, including the provider's initial save effect. Corrupt, invalid, and unsupported current/legacy data remains eligible for removal and current-version replacement.

The location migration creates one lowercase-keyed canonical map from declared locations and inventory-only references. Every surviving inventory item is then mapped to the exact canonical string stored in `locations`, restoring referential equality for the reducer's deletion guard.

### Future-version overwrite prevention

For integer versions above `SCHEMA_VERSION`, `loadState` returns fallback without entering cleanup and leaves the persisted value untouched; `storageWritesEnabled = false` makes the subsequent provider save a no-op. Malformed JSON, invalid version values, and unsupported version 1/2 shapes instead enter cleanup, as intended.

### Exact inventory-to-location references

`normalizeLocations` keeps the first spelling for each lowercase key and includes inventory locations in its candidates. `migrateState` resolves each inventory location through that same map, so each surviving reference exactly equals an entry in the deduplicated `locations` array.
